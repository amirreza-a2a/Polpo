# ADR-008: Agent Working Copy, Isolated Patch Lifecycle, and Optimistic Concurrency Control (OCC) Safety

- **Status:** Proposed (Awaiting Maintainer Approval)
- **Date:** 2026-11-09
- **Scope:** Working Copy Lifecycle, Document Patch Engine, Stale Revision Detection, Multi-Region Edits, Native Editor Integration, Undo/Redo Integrity, OCC Publication
- **Authoritative Baseline:** Commit `25bb95d198c34c035b5d66513166e06494d82cdb`
- **Related ADRs:** ADR-001 (Three-Way Merge Conflict Resolution), ADR-004 (Artifact Lineage & Canonical Publication), ADR-006 (AI LaTeX Repair), ADR-007 (Agent Orchestration & Tool Governance), ADR-009 (Quarto Diagnostics & PDF Repair)
- **Confirmed Requirements:** D-USER-01 (Unified Assistant Scope), D-USER-02 (Supervised Agent Autonomy), D-USER-03 (Document vs Rendering-System Repair)

---

## 1. Context

Polpo is an embedded, local-first document workspace where canonical document state is governed by immutable, versioned files on disk (`output_{job_id}_v{version}.md`) and Optimistic Concurrency Control (OCC) managed by `DocumentPublicationService` ([ADR-004](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/docs/adr/2026-10-22-adr-004-pipeline2-artifact-lineage-and-canonical-publication-contract.md)). Simultaneously, the user interacts with an in-memory draft buffer in `MarkdownEditorController`, which tracks local dirty status (`isDirty`) and maintains an active undo/redo stack (`QUndoStack`).

When the Unified AI Assistant investigates a document repair, analyzes technical diagrams, or proposes publication styling (ADR-007), it frequently generates candidate modifications across multiple document regions. If the assistant were to modify canonical files directly or alter the active editor buffer while the user is typing, it would cause data corruption, race conditions, loss of undo history, and OCC save collisions.

---

## 2. Problem Statement

How should Polpo isolate candidate modifications generated by the Agent so that:
1. The assistant never mutates immutable canonical documents or advances the database version watermark while investigating, planning, or validating changes?
2. The user's active editor buffer and undo/redo history are strictly protected from in-flight agent disruptions?
3. The system reliably detects stale patches if the user edits the document while an agent task is in flight?
4. Multi-region changes (e.g. updating multiple LaTeX formulas or YAML front matter and body text simultaneously) are represented, validated, and applied atomically?
5. Final adoption of agent-proposed changes adheres strictly to the existing Optimistic Concurrency Control (OCC) and three-way merge conflict resolution protocols?

---

## 3. Architectural Forces & Constraints

1. **Canonical Immutability ([`AGENTS.md`](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/AGENTS.md) Rules 8 & 9):** Canonical document files are strictly append-only and immutable. Existing version files are never overwritten in-place.
2. **Raw Text Authority ([`CONTEXT.md`](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/CONTEXT.md) Section 3.4):** Plain text is the single source of truth. CommonMark AST parsing is strictly read-only; AST-to-text re-serialization is forbidden to prevent formatting or whitespace corruption.
3. **OCC Watermark Invariant ([`AGENTS.md`](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/AGENTS.md) Rule 8):** Commits require `base_version == active_canonical_version`. If a concurrent change advanced the version, `StaleDocumentVersionError` must be raised.
4. **Human In-Buffer Safety ([`CONTEXT.md`](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/CONTEXT.md) Section 2.2):** Applying external changes must not discard uncommitted human keystrokes without explicit review.
5. **No Silent Commit:** The Agent must never commit changes to canonical history without explicit human approval.

---

## 4. Confirmed Requirements (Maintainer Settled)

- **D-USER-02 (Supervised Agent Autonomy):** The Agent may create and modify temporary working copies, generate patches, and run local validation workflows. However, applying proposed document changes requires explicit user approval; persistent canonical changes must use existing Editor and OCC workflows; and the Agent must never silently commit changes.

---

## 5. Considered Alternatives

### Alternative A: In-Place Canonical Document Overwrite
- *Description:* Let the agent directly modify `output_{job_id}_v{version}.md` on disk.
- *Rejection Rationale:* Directly violates Polpo's foundational immutability rules. Any crash or rejected proposal leaves disk state corrupt. Completely breaks OCC and audit lineage.

### Alternative B: Direct Editor Buffer Mutation During In-Flight Tasks
- *Description:* Have the agent modify `MarkdownEditorController._source_text` in real-time as tool steps execute.
- *Rejection Rationale:* Disrupts the user's typing focus, corrupts the Qt `QUndoStack`, and causes race conditions if the user edits text concurrently with background agent tool calls.

### Alternative C: Proposed Decision — Isolated `AgentWorkingCopy` and Atomic `PatchSet` Application
- *Description:* The agent operates strictly on an in-memory/scratchpad `AgentWorkingCopy` bound to a specific base canonical version and SHA-256 hash. When candidate changes are validated and approved by the user, the resulting `PatchSet` is applied to the active editor buffer via atomic `QTextCursor` edit blocks or committed via `DocumentPublicationService` under OCC.
- *Selection Rationale:* Completely isolates experimental agent work from canonical storage and user typing; guarantees clean stale-revision detection; preserves full undo/redo capability.

---

## 6. Proposed Decision

We propose establishing the **Agent Working Copy and Patch Architecture** consisting of:
1. An isolated **`AgentWorkingCopy`** entity in `core/entities/agent_working_copy.py`.
2. A typed, line-range and metadata **`DocumentPatch` / `PatchSet`** model in `core/entities/document_patch.py`.
3. A deterministic **Patch Application & Stale-State Engine** in `application/services/document_patch_service.py`.
4. Integration with `MarkdownEditorController` enforcing atomic edit blocks, undo preservation, and OCC save gating.

## 7. Detailed Design

### 7.2 The `AgentWorkingCopy` Aggregate

```python
@dataclass
class AgentWorkingCopy:
    """Isolated document scratchpad for autonomous agent investigation and candidate validation."""
    working_copy_id: str                 # UUID4
    task_id: str                        # Parent AgentTask UUID4
    job_id: int                         # Target document job ID
    base_canonical_version: int         # Canonical version snapshot loaded at start
    base_source_sha256: str             # SHA-256 hash of base source text
    draft_revision: int                 # Editor draft revision at time of copy creation
    current_text: str                   # Active scratchpad Markdown text
    staged_patches: List[DocumentPatch] # Ordered sequence of applied candidate patches
    metadata_overrides: Dict[str, Any]  # Staged front-matter metadata changes
    style_profile_id: Optional[str]     # Assigned PublicationStyleProfile identifier
    status: WorkingCopyStatus           # DRAFT, VALIDATING, VALIDATED, APPLIED, REJECTED, STALE
    created_at: float
    updated_at: float
```

### 7.3 Patch Representation & Grammar

To avoid lossy AST re-serialization, document patches operate strictly on **raw source text lines and token ranges**:

```python
class PatchScope(Enum):
    SOURCE_LINE_RANGE = "SOURCE_LINE_RANGE"  # Exact line interval [start_line, end_line]
    RAW_BLOCK_TOKEN = "RAW_BLOCK_TOKEN"      # Specific fenced raw LaTeX or TikZ block
    METADATA_FIELD = "METADATA_FIELD"        # Front-matter YAML key-value adjustment
    STYLE_PROFILE = "STYLE_PROFILE"          # PublicationStyleProfile assignment

@dataclass(frozen=True)
class DocumentPatch:
    """Atomic modification unit within an AgentWorkingCopy."""
    patch_id: str
    scope: PatchScope
    target_start_line: int              # 1-indexed start line in base text
    target_end_line: int                # 1-indexed end line in base text
    original_text: str                  # Expected original text fragment (for collision detection)
    replacement_text: str               # Proposed replacement text
    change_summary: str                 # Human-readable rationale (English)
    preserved_invariants: Tuple[str, ...] # Invariant assertions (e.g. "formula_syntax_valid")
```

A collection of patches generated for a single task forms a **`PatchSet`**.

### 7.4 Stale Revision & Collision Detection Protocol

Before applying any patch to the working copy or proposing it for final adoption, the engine evaluates four safety preconditions:

1. **Base Version Precondition:** The target document's current canonical version in SQLite must equal `working_copy.base_canonical_version`. If another process advanced the document ($N \to N+1$), the working copy is marked `STALE` and the proposal cannot be adopted directly.
2. **SHA-256 Text Integrity Precondition:** When applying a patch, the engine verifies that the text at `[target_start_line, target_end_line]` matches `patch.original_text` exactly.
3. **Duplicate Fragment Disambiguation:** If `patch.original_text` occurs in multiple locations across the document, the line coordinates disambiguate the target. If line coordinates do not match, the patch is rejected with `AmbiguousPatchTargetError` rather than guessing.
4. **Non-Overlapping Invariant:** Multiple patches in a single `PatchSet` must not overlap line ranges. Overlapping hunks within the same set cause immediate validation failure.

### 7.5 Final Adoption Flow: Native Editor Integration & OCC

When the user clicks "Apply Changes" on an approved proposal:

```mermaid
sequenceDiagram
    participant User as Human User (QML)
    participant AC as AgentController
    participant MEC as MarkdownEditorController
    participant DPS as DocumentPublicationService
    participant DB as SQLite WAL

    User->>AC: Clicks "Apply Changes"
    AC->>MEC: apply_patch_set(patch_set)

    alt Active Editor Has Unsaved Conflicting Edits
        MEC-->>AC: Rejects with EditorDirtyConflictError
        AC-->>User: Prompts: "Editor has unsaved edits. Resolve or save before applying agent changes."
    else Base Version Matches & Buffer Clean
        Note over MEC: Begins atomic edit block (QTextCursor)
        loop For each patch in PatchSet
            MEC->>MEC: Replace exact line range
        end
        Note over MEC: Ends atomic edit block (QUndoStack preserved!)
        MEC->>MEC: Mark buffer dirty (isDirty = True)
        MEC-->>AC: Applied successfully
        AC-->>User: UI reflects applied changes; undoable via Ctrl+Z

        opt User Chooses Immediate Save
            User->>MEC: Clicks "Save" (Ctrl+S)
            MEC->>DPS: commit_source_text(job_id, base_version, text)
            DPS->>DB: Atomic 4-Phase OCC Publication
            DB-->>DPS: Committed version N+1
            DPS-->>MEC: Active version updated to N+1
        end
    end
```

#### Key Invariants of Adoption:
1. **Undo Stack Preservation:** In `MarkdownEditorController`, patches are applied via `QTextCursor.beginEditBlock()` and `QTextCursor.endEditBlock()`. The entire multi-region patch set forms a single undo action. The user can immediately press `Ctrl+Z` to revert the entire agent proposal cleanly.
2. **Zero Silent Persistence:** Applying a proposal modifies the active plain-text buffer and marks `isDirty = True`, but does NOT write to SQLite or disk automatically. The user reviews the syntax-highlighted editor pane and manually saves (or clicks "Apply and Save" with explicit confirmation).
3. **OCC Gating:** When the document is saved, `DocumentPublicationService.publish_version()` verifies that `base_version == latest_canonical_version`. If a concurrent process advanced the version in the background, `StaleDocumentVersionError` is raised, triggering standard three-way merge conflict resolution ([ADR-001](file:///home/amirreza-a2a/DevelopPOlpo/PolpoT/docs/adr/2026-09-18-adr-001-phase10f5-three-way-merge-conflict-resolution.md)).

## 9. Security & Privacy Considerations

1. **Scratchpad Containment:** Working copies exist in RAM or temporary session files under `.pdf_staging/`. They are never exposed to remote processes or accessible outside the local user session.
2. **Sanitized Diff Presentation:** When presenting diffs to the user, sensitive user directories are redacted using the existing sanitization utilities.
3. **No AST Scraping:** Patches are computed directly on plain text lines. There is zero risk of AST parser round-trip bugs corrupting whitespace, mathematical delimiters, or custom macro characters.

---

## 10. Failure & Recovery Behavior

1. **Patch Collision:** If a patch fails line-boundary verification (e.g. because text shifted), the working copy is preserved in `DRAFT` status and an `InvalidPatchTargetError` is reported back to the orchestrator for self-correction.
2. **Abandoned Tasks:** If the user cancels a task or closes the application, the `AgentWorkingCopy` is discarded from memory. Temporary PDF candidate files in `.pdf_staging/` are purged during normal cleanup.
3. **Editor Desynchronization:** If the user edits the document in the editor while an agent task is running, the agent's working copy will detect a `draft_revision` mismatch upon completion. The UI notifies the user: *"Document was modified during agent execution. Review changes against latest draft."*

---

## 11. Consequences

### Positive:
- **Absolute Document Safety:** Canonical document versions are completely insulated from experimental or failing agent steps.
- **Flawless Undo Integration:** Authors retain total control. Any applied agent proposal can be instantly undone with standard `Ctrl+Z`.
- **OCC Compliance:** Reuses the proven `DocumentPublicationService` 4-phase commit protocol without introducing duplicate publication logic.

### Negative / Trade-offs:
- **Memory Overhead:** Holding an in-memory working copy consumes RAM proportional to document size (typically < 1MB for technical documents; completely negligible on modern workstations).
- **Concurrency Locking:** If the user makes substantial structural edits while an agent task is running, the agent's candidate patch may become stale, requiring a re-run against the updated draft.

---

## 12. Migration & Rollout Strategy

1. **Phase 1:** Implement `core/entities/agent_working_copy.py` and `core/entities/document_patch.py`.
2. **Phase 2:** Implement `application/services/document_patch_service.py` with full unit test coverage verifying line replacements and collision rejection.
3. **Phase 3:** Integrate `apply_patch_set` into `MarkdownEditorController`, binding to atomic edit blocks.
4. **Phase 4:** Connect the orchestrator's candidate generation tools to the working copy service.

## 13. Testing & Verification Strategy

- **Unit Tests:**
  - Test `DocumentPatchService` against complex Markdown documents containing tables, math formulas, and TikZ diagrams.
  - Verify rejection of out-of-bounds line coordinates, text mismatches, and overlapping patches.
  - Verify that applying patches to text with duplicate identical lines correctly disambiguates via line coordinates.
- **Integration Tests:**
  - Test `MarkdownEditorController.apply_patch_set()` with PySide6/QML test harness, verifying `isDirty` becomes `True`, the text changes accurately, and `QUndoStack.undo()` cleanly reverts the buffer.
  - Verify that saving an applied patch advances the canonical version watermark monotonically via `DocumentPublicationService`.
